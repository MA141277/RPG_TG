1: 下面是一份可直接粘贴给其他会话评审的版本。
2: # 混合式多会话协同方案（主线程 + 线程内 Sub-Agent）
3: 
4: ## 1. 目标
5: 
6: 本方案用于在 Codex 场景下组织多个“主会话”协同处理同一项复杂任务，并允许各主会话在必要时使用线程内 sub-agent 提升局部执行效率。
7: 
8: 目标是建立一套可重复、可审计、可升级的协同机制，避免多个会话互相覆盖、重复劳动、状态失真或验收口径不一致。
9: 
10: 本方案采用单 Controller 治理模式：
11: - 只有 1 个 controller 主会话负责拆解、派发、追踪、升级、验收和整合。
12: - 其他主会话只承担明确角色，不共享调度权。
13: - 各主会话之间不直接相互指挥。
14: - 线程内 sub-agent 仅作为局部执行加速器，不承担跨线程协调职责。
15: 
16: ## 2. 适用范围
17: 
18: 适用于以下类型任务：
19: - 一个目标可拆分为多个独立子任务
20: - 需要实现、评审、测试、文档等角色分工
21: - 需要主会话长期存在并可单独续跑
22: - 需要清晰的状态追踪和统一验收
23: 
24: 不适用于以下类型任务：
25: - 多人必须同时修改同一批文件
26: - 需求尚未收敛，任务边界不清
27: - 极小型单点修复
28: - 高耦合、必须共享完整上下文才能推进的工作
29: 
30: ## 3. 架构角色
31: 
32: ### 3.1 Controller 主会话
33: 
34: 职责：
35: - 维护唯一任务真相源
36: - 拆分任务并定义边界
37: - 创建和续跑 worker 主会话
38: - 追踪状态并处理升级
39: - 收集实现、评审、QA 结果
40: - 做最终验收和整合
41: 
42: 约束：
43: - 不直接承担大规模实现工作
44: - 不把调度权转交给任何其他会话或 sub-agent
45: - 所有“完成”判定都由 controller 作出
46: 
47: ### 3.2 Implementer 主会话
48: 
49: 职责：
50: - 负责某个明确子任务的实现
51: - 在自己的写入范围内完成代码或配置修改
52: - 自行提供验证证据
53: - 完成后回报标准化状态
54: 
55: 约束：
56: - 不修改未授权文件
57: - 不自判最终完成
58: - 不直接要求 reviewer 或 QA 采纳结论
59: 
60: ### 3.3 Reviewer 主会话
61: 
62: 职责：
63: - 对实现结果做规范和质量评审
64: - 输出明确 findings 和结论
65: - 判断是否存在越权、缺失、回归风险、测试缺口
66: 
67: 约束：
68: - 不直接改代码
69: - 不代替 implementer 修复问题
70: - 不改变任务定义
71: 
72: ### 3.4 QA 主会话
73: 
74: 职责：
75: - 做需求验证、回归验证、冒烟验证
76: - 输出可复现验证结果
77: - 明确指出失败项和复现方法
78: 
79: 约束：
80: - 不承担实现
81: - 不替代 reviewer 做规范审查
82: - 不绕过 controller 直接决定通过
83: 
84: ### 3.5 Docs 主会话（可选）
85: 
86: 职责：
87: - 汇总变更说明、交付摘要、操作文档
88: - 基于已确认结果产出文档
89: 
90: 约束：
91: - 不定义需求
92: - 不替代实现和验收
93: 
94: ### 3.6 线程内 Sub-Agent
95: 
96: 职责：
97: - 在某个主会话内部处理局部、明确、可并行的小任务
98: - 例如：局部补丁、独立测试、日志分析、文档整理
99: 
100: 约束：
101: - 只能服务所属主会话
102: - 不跨主会话通信
103: - 不承担跨线程协调
104: - 不修改当前主会话写入范围之外的文件
105: 
106: ## 4. 运行原则
107: 
108: ### 4.1 单一调度权
109: 
110: 所有任务调度、状态确认、升级处理、验收整合，统一由 controller 完成。
111: 
112: ### 4.2 工件协同，不靠聊天记忆
113: 
114: 各主会话之间不依赖会话历史共享上下文，而应依赖以下工件：
115: - 任务说明
116: - 文件范围
117: - 接口约定
118: - 状态台账
119: - 评审记录
120: - QA 记录
121: - 决策记录
122: 
123: ### 4.3 写入域隔离
124: 
125: 任何时刻，不允许两个 implementer 主会话同时修改同一写入域。
126: 
127: ### 4.4 角色职责单一
128: 
129: 实现、评审、验证、文档应尽量分离，避免“自己实现、自己评审、自己通过”。
130: 
131: ### 4.5 统一状态协议
132: 
133: 所有主会话必须用统一格式回报状态，避免自由发挥。
134: 
135: ## 5. 协同工件规范
136: 
137: 建议统一维护以下工件。即使不写入仓库，也建议 controller 在任务上下文中显式维护这些内容。
138: 
139: ### 5.1 任务总说明
140: 
141: 建议命名：
142: `mission.md`
143: 
144: 内容包括：
145: - 目标
146: - 范围
147: - 非目标
148: - 成功标准
149: - 全局约束
150: - 角色分工
151: 
152: ### 5.2 任务看板
153: 
154: 建议命名：
155: `task-board.md`
156: 
157: 内容包括：
158: - Task ID
159: - 任务名称
160: - 负责线程
161: - 当前状态
162: - 依赖关系
163: - 最近更新时间
164: - 下一步动作
165: 
166: ### 5.3 接口约定
167: 
168: 建议命名：
169: `interfaces.md`
170: 
171: 内容包括：
172: - 各子任务之间的输入输出
173: - 类型、函数、路径、契约
174: - 约束与兼容性要求
175: 
176: ### 5.4 评审日志
177: 
178: 建议命名：
179: `review-log.md`
180: 
181: 内容包括：
182: - Task ID
183: - Reviewer 结论
184: - Findings
185: - 严重级别
186: - 是否已处理
187: 
188: ### 5.5 QA 日志
189: 
190: 建议命名：
191: `qa-log.md`
192: 
193: 内容包括：
194: - Task ID
195: - 验证命令
196: - 验证环境
197: - PASS/FAIL
198: - 失败复现方式
199: - 结论
200: 
201: ### 5.6 决策日志
202: 
203: 建议命名：
204: `decisions.md`
205: 
206: 内容包括：
207: - 决策编号
208: - 背景
209: - 备选方案
210: - 最终选择
211: - 决策人
212: - 生效范围
213: 
214: ## 6. 状态机
215: 
216: 每个主会话必须从以下状态中选择，不允许自定义状态名。
217: 
218: - `NEW`
219: - `DISPATCHED`
220: - `RUNNING`
221: - `NEEDS_CONTEXT`
222: - `BLOCKED`
223: - `DONE_PENDING_REVIEW`
224: - `REVIEW_FAILED`
225: - `DONE_PENDING_QA`
226: - `QA_FAILED`
227: - `ACCEPTED`
228: - `CLOSED`
229: 
230: 状态说明：
231: 
232: ### 6.1 NEW
233: 任务已定义，但未派发。
234: 
235: ### 6.2 DISPATCHED
236: controller 已派发给目标主会话，尚未正式执行或刚启动。
237: 
238: ### 6.3 RUNNING
239: 目标主会话正在处理任务。
240: 
241: ### 6.4 NEEDS_CONTEXT
242: 主会话无法继续，需要 controller 补充上下文、决策或约束。
243: 
244: ### 6.5 BLOCKED
245: 主会话遇到无法自行解决的阻塞问题，例如依赖缺失、写入冲突、任务边界错误、外部条件不满足。
246: 
247: ### 6.6 DONE_PENDING_REVIEW
248: 实现已完成，等待 reviewer 评审。
249: 
250: ### 6.7 REVIEW_FAILED
251: reviewer 发现问题，任务未通过评审。
252: 
253: ### 6.8 DONE_PENDING_QA
254: 评审已通过，等待 QA 验证。
255: 
256: ### 6.9 QA_FAILED
257: QA 验证未通过，需回到实现修复。
258: 
259: ### 6.10 ACCEPTED
260: controller 确认该任务通过并接受结果。
261: 
262: ### 6.11 CLOSED
263: 该主会话任务生命周期结束，不再继续处理。
264: 
265: ## 7. 标准执行流程
266: 
267: ### 7.1 启动阶段
268: 1. controller 编写并确认 mission
269: 2. controller 拆分任务并形成 task-board
270: 3. controller 明确每个任务的写入域、输入、输出、依赖
271: 4. controller 为可并行子任务创建 implementer 主会话
272: 5. controller 创建 reviewer 和 QA 主会话，作为后续统一入口
273: 
274: ### 7.2 实现阶段
275: 1. implementer 主会话读取任务说明
276: 2. implementer 在授权写入域内完成实现
277: 3. implementer 做最小必要验证
278: 4. implementer 用统一格式上报 `DONE_PENDING_REVIEW`
279: 
280: ### 7.3 评审阶段
281: 1. controller 将实现结果交给 reviewer 主会话
282: 2. reviewer 输出 findings 和结论
283: 3. 若失败，controller 将问题回派给原 implementer 或专用 fix 线程
284: 4. 若通过，controller 将状态推进到 `DONE_PENDING_QA`
285: 
286: ### 7.4 验证阶段
287: 1. controller 将已通过评审的结果交给 QA 主会话
288: 2. QA 运行验证并产出记录
289: 3. 若失败，controller 回派修复
290: 4. 若通过，controller 将任务标记为 `ACCEPTED`
291: 
292: ### 7.5 整合阶段
293: 1. 所有子任务 `ACCEPTED` 后，controller 做最终整合
294: 2. 必要时启动 docs 主会话生成交付摘要
295: 3. controller 输出总验收结论
296: 4. controller 关闭相关主会话
297: 
298: ## 8. 自动化编排规则
299: 
300: 本方案采用高自动模式。
301: 
302: controller 应自动完成以下动作：
303: - 判断任务是否可并行
304: - 判断是否需要新建主会话
305: - 判断任务是否应进入评审
306: - 判断任务是否应进入 QA
307: - 周期性读取各主会话状态
308: - 对 `NEEDS_CONTEXT` 和 `BLOCKED` 做升级处理
309: - 对评审失败和 QA 失败自动回派修复
310: - 统一推进任务状态
311: 
312: controller 仅在以下情况请求人工介入：
313: - 需求冲突
314: - 任务拆分错误
315: - 写入域冲突
316: - reviewer 结论与原始要求冲突
317: - 多种技术路径需要业务取舍
318: - 同一任务连续失败达到升级阈值
319: 
320: ## 9. 升级规则
321: 
322: ### 9.1 NEEDS_CONTEXT
323: 处理方式：
324: - controller 补充上下文后原线程继续
325: - 如果说明原任务定义不完整，controller 更新 mission 或 task-board
326: 
327: ### 9.2 BLOCKED
328: 处理方式：
329: - controller 判断是环境问题、拆分问题、权限问题还是依赖问题
330: - 必要时重新拆分任务或改派线程
331: 
332: ### 9.3 REVIEW_FAILED
333: 处理方式：
334: - 回原 implementer 修复
335: - reviewer 不代修
336: - 修复后必须重新评审
337: 
338: ### 9.4 QA_FAILED
339: 处理方式：
340: - 回 implementer 或 fix 线程修复
341: - 修复后必须重新验证
342: 
343: ### 9.5 连续失败阈值
344: 同一任务连续 2 次进入 `REVIEW_FAILED` 或 `QA_FAILED`，应升级为人工关注项。
345: 
346: ## 10. 主线程与 Sub-Agent 的关系
347: 
348: 本方案优先使用“多个主线程”承载主要协同，因为主线程更适合：
349: - 长任务
350: - 独立续跑
351: - 明确角色
352: - 可审计协同
353: - 后续评审
354: 
355: sub-agent 仅在以下情况作为补充：
356: - 某主线程内部还存在 2 个以上互不冲突的局部任务
357: - 某主线程希望把搜索、测试、总结等辅助工作拆开
358: - 局部工作有明确边界且不会影响主线程职责边界
359: 
360: 禁止以下行为：
361: - controller 把调度职责外包给 sub-agent
362: - sub-agent 直接跨主线程传递指令
363: - 不同主线程各自再开 sub-agent 去修改同一写入域
364: 
365: ## 11. 输出协议
366: 
367: 所有主会话统一按以下模板回报，避免自由格式。
368: 
369: ```text
370: Status: <NEW | DISPATCHED | RUNNING | NEEDS_CONTEXT | BLOCKED | DONE_PENDING_REVIEW | REVIEW_FAILED | DONE_PENDING_QA | QA_FAILED | ACCEPTED | CLOSED>
371: Task: <Task ID>
372: Role: <Controller | Implementer | Reviewer | QA | Docs>
373: Summary:
374: - <已完成事项 1>
375: - <已完成事项 2>
376: 
377: Files Changed:
378: - <path 1>
379: - <path 2>
380: 
381: Validation:
382: - Command: <命令>
383: - Result: <PASS | FAIL | NOT RUN>
384: - Notes: <补充说明>
385: 
386: Findings:
387: - <如无则写 None>
388: 
389: Risks:
390: - <风险 1>
391: - <风险 2>
392: 
393: Needs From Controller:
394: - <需要补充的上下文/决策/资源；如无则写 None>
395: 
396: Next Recommended Step:
397: - <建议 controller 的下一步动作>
398: 12. Controller Prompt 模板
399: 你是本项目的唯一 Controller 会话。
400: 你的职责只有 6 件事：
401: 拆分任务
402: 定义每个任务的边界、输入、输出和写入域
403: 创建和续跑其他主会话
404: 跟踪状态并处理升级
405: 将实现结果送评审和 QA
406: 做最终验收与整合
407: 你不是主实现者，不做大规模编码，不把调度权转交给其他会话。
408: 工作规则：
409: 所有任务状态必须使用统一状态机
410: 不允许两个 implementer 会话同时修改同一写入域
411: 所有“完成”结论都由你确认
412: reviewer 只评审，不改代码
413: QA 只验证，不实现
414: 只有在局部明确、边界清楚时，才允许某主会话在线程内部使用 sub-agent
415: 当遇到需求冲突、任务拆分错误、写入冲突、连续失败时，升级给人工
416: 请先输出：
417: 任务拆分结果
418: 每个任务的写入域
419: 每个任务对应的主会话角色
420: 依赖关系
421: 下一步派发顺序
422: 后续每次更新都必须使用统一输出协议。
423: 13. Implementer Prompt 模板
424: 你是一个 Implementer 主会话。
425: 你的任务是完成被分配的单一子任务，只能在授权范围内工作。
426: 你的规则：
427: 只处理当前任务，不扩展范围
428: 只修改授权写入域
429: 完成后不能自判最终完成，只能上报 DONE_PENDING_REVIEW
430: 必须提供最小必要验证证据
431: 如缺少上下文，返回 NEEDS_CONTEXT
432: 如遇阻塞，返回 BLOCKED
433: 你必须重点关注：
434: 当前任务目标
435: 输入输出契约
436: 允许修改的文件范围
437: 禁止触碰的范围
438: 必要测试或验证命令
439: 输出必须使用统一输出协议。
440: 14. Reviewer Prompt 模板
441: 你是一个 Reviewer 主会话。
442: 你的职责是评审实现结果是否满足任务要求，并识别质量问题。你不修改代码，不代替实现者修复问题。
443: 你必须关注：
444: 是否满足任务说明
445: 是否越权修改
446: 是否引入明显回归风险
447: 是否缺失必要测试或验证
448: 是否存在明显实现质量问题
449: 你的结论只能是以下两类之一：
450: 通过，建议进入 QA
451: 不通过，列出 findings 并退回修复
452: 请不要给宽泛建议，所有 findings 都应尽量具体、可操作、可验证。
453: 输出必须使用统一输出协议。
454: 15. QA Prompt 模板
455: 你是一个 QA 主会话。
456: 你的职责是验证实现结果是否满足预期行为，并检查回归风险。你不负责实现，也不负责代码评审。
457: 你必须关注：
458: 需求是否成立
459: 关键路径是否可运行
460: 回归是否出现
461: 失败是否可复现
462: 验证证据是否完整
463: 如果验证失败，请提供：
464: 失败场景
465: 复现步骤
466: 实际结果
467: 期望结果
468: 结论
469: 输出必须使用统一输出协议。
470: 16. 推荐协同策略
471: 推荐采用以下角色分工：
472: 1 个 controller 主会话
473: N 个 implementer 主会话，按写入域拆分
474: 1 个 reviewer 主会话
475: 1 个 QA 主会话
476: 1 个 docs 主会话（可选）
477: 推荐拆分维度：
478: 按模块
479: 按文件域
480: 按功能子任务
481: 按验证职责
482: 不推荐拆分维度：
483: 随机拆
484: 让多个实现者同时改同一模块核心文件
485: 把“实现 + 评审 + 验证”塞给同一个主会话
486: 17. 评审重点建议
487: 请重点评审以下问题：
488: 单 controller 治理是否足够稳健
489: 状态机是否完整且无歧义
490: 写入域隔离是否可执行
491: reviewer 与 QA 的边界是否清楚
492: 主线程与 sub-agent 的分层是否合理
493: 自动化升级规则是否过松或过严
494: 输出协议是否足以支撑后续自动整合
495: 18. 结论
496: 这套方案的核心不是让多个主会话共享“思维”，而是让它们共享一套统一的工件、状态机、角色边界和升级规则。
497: 主会话负责长期、独立、可审计的协作。
498: sub-agent 负责线程内部的局部加速。
499: controller 是唯一调度者和最终验收者。
500: 如果任务边界清晰、写入域隔离得当，这套方案可以稳定支撑“并行实现 + 独立评审 + 独立 QA + 最终整合”的混合式多会话协同。
