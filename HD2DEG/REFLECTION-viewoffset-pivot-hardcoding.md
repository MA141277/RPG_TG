# 反思：透视锚点与「画面偏移」上的硬编码上限

## 现象

在调试 2.5D 雪地、脚底高亮、Q/E 绕轨时，多次出现：

- 用**魔法数字**限制「透视 pivot 相对脚底最多下移多少像素」（例如 `52`、`footRef + 52`）；
- 或用**固定比例/条带高度**决定雪地 `maxGroundY`（如 `h*0.88`、`+32` 等）。

短期可能「压住」某个 bug（例如 offset 极大时 pivot 被钳到画布最底、与 `footScreenAnchor` 不一致导致黄点偏下），但会带来**反复踩坑**：

1. **与产品控件矛盾**：`viewOffsetY` 在 UI 上可以是 ±500 或更大（`bumpMax` 还会扩表），代码里却写死「最多相对脚底下移 52px」——用户调得动滑杆，却调不动真实行为，表现为「上限被写死」「偏移不好使」。
2. **同一问题多次回归**：修 A  bug 引入硬编码 → 修 B  bug 又加另一套硬编码 → 两套互相打架或掩盖根因（应用是 **pivot 与反算采样点不一致**，而不是「需要神秘常数 52」）。
3. **可维护性差**：半年后没人记得 52 代表什么；改分辨率或 UI 后常数失效。

## 根因（应优先修的）

- **语义不一致**：透视用 `getPivot().py`，高亮/反算却用「未与 pivot 对齐」的屏幕 y（例如 raw `footY`），再靠「把 pivot 往下限死」凑合 —— 应统一数据源，而不是加像素帽。
- **把「构图滑杆」与「安全钳制」混写在一处**：`viewOffsetY` 应完整进入公式；画布边界用 **`clamp(地平线+2, h-2)`** 等与**画布几何**相关的规则即可，不要另加与**用户设定无关**的像素预算。

## 本次代码原则（已落实方向）

- **`getPivotForCanvas`**：只做 `baseY + viewOffsetY` 再 **`clampY` 到地平线～画布底`**，**不再** `Math.min(merged, footRef + 常数)`。
- **雪地 `maxGroundY`**：改为 **`h`**，不再用 `pivot+18`、`rawFoot+32`、`h*0.88` 等拼出来的条带上限；若底部透视有瑕疵，应单独用**可调参数**或**与 camDist/forwardScale 联动**的推导，而不是写死像素。
- **可调项**：若将来需要「脚底以下多画几行」这类能力，应暴露为 **`animator` 字段 + UI 滑杆**或从**已有滑杆**推导，并在注释里写清**与哪个物理量同源**。

## 协作与自检清单（以后改类似逻辑前）

1. 任何 `Math.min(..., foot + N)`、`N = 52` 这类写法：先问 **N 的用户可见来源是什么**；没有则禁止合并进主路径。
2. **反算 / 正算 / 高亮**是否共用**同一套** `getPivot`（或同一套屏幕锚点定义）？不一致则先对齐，再加辅助逻辑。
3. **滑杆范围**与**代码钳制**是否一致？扩 `bumpMax` 时是否同步检查**业务层**是否还有隐式上限。
4. 若必须加「保险」：优先 **与画布尺寸成比例**（且系数来自命名常量并集中配置），或 **显式 UI**，避免散落魔法数。

## 一句话

**用户能调的，代码里就不要用无出处的常数替他「封顶」；真需要顶，就让它也能被调或从同一数据源推导。**
