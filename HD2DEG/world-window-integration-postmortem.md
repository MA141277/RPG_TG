# 世界窗口集成事故检讨

## 结论

这次问题的本质不是“需求太复杂”，而是我在实现“把人物/建筑生成入口搬到世界窗口”这个 UI 改动时，**越过了需求边界，连带修改了原本已经可用的人物生成链路**，导致一个本应局部的界面集成任务，演变成了对既有协议、交互入口、建筑重建流程的同时重构，最终引入回归。

## 用户原始需求

用户的核心诉求是：

1. 在像素世界里增加类似人物八向图的建筑 AI 工作流。
2. 在 `tuning`/世界窗口里输入提示词。
3. Gemini 生成建筑三视图。
4. 本地自动去背景、识别主体并切片。
5. 生成建筑并供玩家放置。

后续又补充了几个明确约束：

1. 建筑三视图命名应为 `正 / 侧 / 俯`，不是 `左 / 右 / 俯`。
2. 建筑切片不能沿用人物的“单连通主体”思路，因为建筑中空很正常。
3. 贴图不能只有模型没有颜色。
4. 生成人物和建筑的提示词界面要搬到世界窗口里。
5. **人物原本已可用的参考图链路不能被破坏。**

## 这次犯的错误

### 1. 把“UI 搬运”做成了“链路重写”

正确做法应该是：

- 只把按钮、提示词输入框、状态显示、预览移动到世界窗口 HUD。
- 保持人物既有生成逻辑不动。

但我实际做成了：

- UI 搬运
- 人物生成协议修改
- 建筑生成新链路接入
- 建筑贴图与体素运行时扩展
- 交互入口重绑

这属于**在没有用户要求的情况下扩大改动面**。

### 2. 在没有证明原链路坏掉之前，擅自改人物参考图协议

用户后来明确指出：

> “之前一直好使啊，自从让你加到世界里之后就坏了”

这句话其实已经说明一个重要事实：

- 原先人物参考图生成链路是能用的。
- 问题发生在我集成世界窗口之后。

但我当时没有第一时间坚持“恢复原逻辑、隔离 UI 改动”，而是继续去猜：

- `images/edits` 是否不兼容
- 是否应该改成 `chat/completions` 多模态
- 是否该自动回退到普通生图

这导致我把“定位回归”做成了“继续改协议”，进一步放大了不确定性。

### 3. 用 fallback 掩盖主问题

当人物参考图返回：

- `data: []`
- 没有 `b64_json`

我第一反应是加“回退到普通生图”。

这在工程上是错误决策，因为用户明确要的是：

- **参考图必须能传进去**
- 不是“失败了就先糊一张普通图”

这个 fallback 的问题在于：

1. 它没有解决主问题。
2. 它会掩盖协议层的真实失败原因。
3. 它让用户看到“似乎还能出图”，但输出已经偏离原工作流。

这是典型的“补丁式修复替代根因修复”。

### 4. 没有第一时间把人物和建筑链路隔离

这次需求里其实有两条独立链路：

1. 人物参考图生成链路
2. 建筑三视图生成与重建链路

我在实现时让两条链路共享了太多变更上下文，导致：

- 改建筑时碰到了人物
- 改 HUD 时碰到了人物协议
- 改点击入口时影响了整个世界窗口交互

如果一开始就坚持：

- 人物链只搬 UI，不动底层
- 建筑链单独新增

回归范围会小很多。

### 5. 命名和语义没有完全贴合建筑工作流

建筑三视图一开始被我写成了：

- `左视图 / 右视图 / 俯视图`

这是把人物方向感带进了建筑正交图命名里，和用户明确要求的：

- `正视图 / 侧视图 / 俯视图`

不一致。

这不仅是文案问题，也会污染后续：

- 字段名
- 贴图映射
- 认知模型

属于术语使用不严谨。

### 6. 建筑切片起初沿用了人物“连通块”思路

建筑视图里存在：

- 窗洞
- 门洞
- 骑楼
- 柱廊
- 天井

所以不能把“视图主体必须是一个连通块”当成前提。

我一开始仍然沿用了人物切片里的连通域思路，这是错误的迁移复用。后续虽然改成了按颜色列区段识别，但这个错误本来应该在设计阶段就避免。

### 7. 没有先做最小验证闭环

本来应当先验证三个最小闭环：

1. 世界窗口能否稳定打开。
2. 人物原链路在新入口下是否仍然可用。
3. 建筑新链路是否独立可用。

但我在还没有把这三个点逐一验证前，就继续叠加：

- HUD 生成区
- AI 建筑放置
- 彩色贴图投射
- 术语修正

这让排错顺序变差。

## 直接原因

这次回归的直接原因可以归纳为三条：

1. **把局部 UI 改动扩大成了底层协议改动。**
2. **在用户已经说明“以前能用”的前提下，没有优先回归原链路。**
3. **遇到协议失败时先加 fallback，而不是先恢复稳定性。**

## 更深层原因

更深层的问题是执行策略失衡：

- 过度主动
- 改动面过大
- 缺少“保守集成”的边界意识

换句话说，问题不是不会做，而是**做得太多、太快、同时改了太多层**。

## 正确的做法应该是什么

如果重新做一遍，正确顺序应该是：

1. 先只移动 UI 到世界窗口 HUD。
2. 人物生图继续使用原来完全不动的逻辑。
3. 验证人物仍然可用。
4. 再独立接入建筑三视图生成。
5. 再独立接入建筑切片与体素重建。
6. 最后再补建筑贴图、命名、交互优化。

也就是遵循：

- **先保原有可用**
- **再增新功能**
- **一次只动一层**

## 后续约束

以后处理同类需求时，应遵守以下约束：

1. 如果用户说“之前是好的”，优先恢复原链路，不擅自重写协议。
2. UI 搬运默认不改底层逻辑，除非用户明确要求。
3. 不能用 fallback 掩盖主链路失败，尤其当用户明确要求某能力必须工作时。
4. 新功能必须与旧链路隔离，避免交叉回归。
5. 命名必须严格跟用户领域术语一致，不能凭类比迁移。
6. 每完成一层改动，先验证再继续叠加下一层。

## 对这次问题的负责结论

这次事故的责任在于我没有把“集成”当作保守操作，而把它做成了“顺手优化和改造”的机会，最终破坏了原有稳定功能。

最该反省的一点是：

**当用户要求的是“把功能放进世界窗口”，我应该优先保证“原功能在新入口下仍然按原方式工作”，而不是顺势重构人物生成协议。**

## 当前最合理的修复原则

接下来应坚持以下原则：

1. 人物链路回归到原始可用状态。
2. 世界窗口只作为人物链路的新入口，不改变其底层协议。
3. 建筑链路单独推进，绝不再影响人物。
4. 任何新改动都先验证最小闭环。
