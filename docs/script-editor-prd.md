# 剧本编辑器 PRD

本文整理当前已确认的剧本编辑器需求，作为后续详细规格、实施计划和执行队列的产品输入。本文关注创作者工作流、核心对象能力、编辑器交互方式，以及当前仍需进一步明细化的事项。

## 1. 产品目标

本剧本编辑器的目标不是做一个面向技术表结构的 JSON 编辑器，而是做一个面向内容创作者的中文创作工作台。

核心目标如下：

- 让创作者按创作流程而不是按底层数据表完成内容搭建。
- 让创作者在不写 TypeScript 的前提下，完成人物、城市、建筑物、剧情、对话、事件和小游戏绑定的内容创作。
- 保持产出仍为项目当前可接受的合规 `scenario-pack`，不引入新的运行时体系。
- 让事件负责编排、对话负责演出、小游戏绑定负责调用现有预制玩法，而不是在编辑器内重写玩法机制本身。

## 2. 核心设计原则

### 2.1 创作者流程优先

- 编辑器的第一优先需求是工作台本身。
- 工作台必须按创作者的设计流程组织，而不是直接把底层对象表平铺给用户。
- 主要创作流程采用“剧情编排流”：
  - 人物与世界基础
  - 对话与事件
  - 功能绑定
  - 预览与导出

### 2.2 全中文界面

- 编辑器中不应出现英文标题、英文栏目名或英文操作按钮。
- 导航、分栏、说明文案、弹窗标题、错误提示都应以中文呈现。

### 2.3 结构化选择优先

- 条件判断、触发方式、人物类型、菜单功能类型、小游戏绑定类型等，优先使用下拉框、单选、选择器等结构化方式。
- 不要求创作者直接编辑底层结构化 JSON。

### 2.4 预制能力复用

- 剧情编辑器不负责实现新的交易、战斗或小游戏底层机制。
- 编辑器只负责把这些能力作为可配置入口挂接到人物、事件、城市、建筑物和剧情链路中。

### 2.5 不脱离现有项目能力，但允许在其上扩展

- 本 PRD 不应脱离当前项目已有的运行时能力、城市 / 建筑交互模式、事件系统、对话系统和小游戏调用方式。
- 编辑器应以“复用现有正式能力”为前提，而不是凭空定义一套与项目现状无关的新系统。
- 同时，编辑器不应把当前项目中的既有城市、建筑、菜单功能或交互入口写死成不可变模板。
- 正确方向应是：
  - 基于现有项目中已经存在的功能族和交互能力提供默认模板
  - 允许创作者在这些正式能力之上自由组合、重命名、替换和扩展

### 2.6 预览必须内建

- 编辑器必须内置预览能力，不能要求创作者每次导出后再去游戏里盲测。
- 预览采用混合模式：
  - 结构预览
  - 演出预览

## 3. 范围

本 PRD 的核心对象能力包括：

- 人物
- 城市
- 建筑物
- 对话
- 事件
- 剧情
- 小游戏绑定

这些对象都应成为编辑器中的正式对象，而不是临时表项或隐藏配置。

## 4. 编辑器工作台需求

### 4.1 工作台优先级

编辑器工作台本身是当前第一优先需求，应先于单一对象编辑器定义。

### 4.2 工作台结构与布局

本 PRD 中，工作台布局直接收口为固定工作模式，不再作为开放问题保留。

工作台采用“顶部项目栏 + 左侧导航区 + 中央编辑区”为默认主布局，预览与校验作为按需打开的辅助区接入。

具体如下：

- 顶部项目栏
  - 用于展示项目标题、当前状态、保存、校验、导出等全局操作
- 左侧导航区
  - 上半部分为一级导航
  - 下半部分为当前导航下的对象列表或对象树
- 中央编辑区
  - 用于承载当前选中对象的正式编辑表单与分栏
- 预览与校验辅助区
  - 默认收起
  - 由创作者在需要时主动打开
  - 打开后可作为右侧侧栏或覆盖层呈现

一级导航最终定为：

- 项目总览
- 人物与世界
- 对话与事件
- 功能绑定
- 预览与导出

其中：

- 项目总览负责项目状态、工作台摘要和全局进度入口
- 人物与世界负责人物、城市、建筑物
- 对话与事件负责对话、事件、剧情关联
- 功能绑定负责交易入口、菜单功能、小游戏绑定
- 预览与导出负责结构检查、演出预览、校验和导出

默认进入页定为“项目总览”。

### 4.2.1 项目总览页职责

“项目总览”不是空的欢迎页，也不是单纯展示项目标题的封面页，而应作为创作者进入编辑器后的正式首页。

项目总览页至少应承载以下四类信息：

- 项目状态
- 创作进度
- 风险与阻塞
- 下一步操作入口

项目状态区至少应展示：

- 当前项目名称
- 当前剧本包的基础说明
- 最近一次保存、校验、导出状态
- 当前是否满足“可导出且可运行”的基本条件

创作进度区至少应展示：

- 人物、城市、建筑物、对话、事件、剧情、小游戏绑定等核心对象的当前数量
- 哪些对象族已经开始创作
- 哪些对象族仍为空白或明显未完成

风险与阻塞区至少应展示：

- 当前导出阻塞数量
- 当前缺失引用或关键配置缺口的摘要
- 当前最需要创作者优先处理的问题

下一步操作入口至少应支持：

- 继续编辑最近一次操作的对象
- 进入当前最需要补齐的对象族
- 直接进入校验
- 直接进入导出

项目总览页的目标不是替代各对象页，而是帮助创作者在进入项目后第一时间回答以下问题：

- 这个项目现在写到哪一步了
- 还缺什么
- 哪些问题会阻止运行
- 我下一步最应该去哪里继续写

### 4.2.2 项目总览页边界

项目总览页应严格控制边界，不应膨胀成另一个全能编辑页。

项目总览页不应承担：

- 具体对象字段的深度编辑
- 完整的对话、事件或人物表单修改
- 替代正式对象页的主编辑职责

也就是说，项目总览负责判断全局状态与引导下一步，而不是把真正的创作编辑挤到首页完成。

左侧导航区与中央编辑区的关系应遵循以下原则：

- 一级导航负责切换创作阶段
- 对象列表负责切换当前编辑对象
- 中央编辑区始终只聚焦一个当前对象，避免同屏堆叠多个对象表单

预览与校验辅助区与中央编辑区的关系应遵循以下原则：

- 预览与校验不是创作者默认必须常驻关注的区域
- 默认创作动线应聚焦“左侧导航切换对象 + 中央编辑区编辑内容”
- 预览与校验在需要时再打开，而不是默认占据主工作空间
- 校验结果中的问题应可直接回跳到中央编辑区对应位置
- 预览与校验打开后，仍应保持与当前编辑对象联动，不脱离当前工作台上下文

对于小游戏这类需要完整可玩预览的对象，预览区应允许切换到“扩展预览层”：

- 扩展预览层从当前工作台上下文中打开
- 可临时覆盖中央编辑区
- 关闭后回到原编辑对象与原滚动位置
- 不脱离当前工作台，不跳去独立新页面

### 4.3 界面要求

- 全中文标题和操作文案
- 可视化列表与表单组合
- 适合策划连续创作的布局
- 不采用面向程序员的原始 JSON 页面作为默认工作界面
- 默认采用“左侧切换对象，中央完成编辑”的主工作模式
- 预览区和校验区属于按需打开的辅助能力，而不是默认常驻主区
- 不把预览区和校验区拆成两个互相跳转的独立主页面
- 不要求创作者在“编辑页 / 预览页 / 校验页”之间来回切换才能完成一次基本创作闭环

### 4.4 条件编辑要求

- 条件配置必须采用结构化选择方式
- 支持通过下拉框选择条件类型
- 支持通过下拉框选择比较运算符
- 支持以清晰的组合方式表达 `all / any / not`

## 5. 人物需求

### 5.1 人物统一模型

- 人物是统一对象，不拆成 NPC 表和角色表两套结构。
- `NPC / 角色` 只是人物类型字段，不是结构分叉。
- 两种类型可以相互转换。
- 玩家进入游戏时只能从“角色”类型人物中选择可操控对象。

### 5.2 人物导航与操作

在编辑器中，人物应具备以下基础操作：

- 人物列表
- 新增人物
- 删除人物
- 点击人物进入详情编辑

### 5.3 人物详情分栏

人物详情页至少包含以下分栏：

- 属性
- 对话
- 交易
- 事件

### 5.4 属性分栏

人物属性分栏采用“固定基础字段 + 可扩展属性键值对”的方式：

- 固定基础字段用于承载人物的正式基础资料
- 扩展属性支持新增、删除、修改
- 当前阶段不进入“全局 schema 自定义”阶段

### 5.5 交易分栏

- 交易分栏按“能力绑定入口”处理
- 该分栏负责声明人物是否具备交易能力，以及绑定哪个交易入口
- 该分栏不负责编辑商店库存、价格体系或买卖底层机制

### 5.6 对话与事件分栏

- 对话分栏用于承接人物相关的对话入口与内容关联
- 事件分栏用于承接人物相关事件入口与触发配置

对于人物页中的“对话分栏”，进一步明确其边界如下：

- 该分栏负责查看该人物关联了哪些对话
- 该分栏负责新增、删除、重排人物与对话之间的关联
- 该分栏可以提供“新建对话并关联”与“跳转到正式对话页编辑”的入口
- 该分栏不承担完整对话节点、分支、跳转和演出内容的深度编辑

也就是说，人物页中的“对话分栏”是关系组织入口，不是第二套对话编辑器。

对于人物页中的“事件分栏”，进一步明确其边界如下：

- 该分栏负责查看该人物关联了哪些事件
- 该分栏负责新增、删除、重排人物与事件之间的关联
- 该分栏可以提供“新建事件并关联”与“跳转到正式事件页编辑”的入口
- 该分栏不承担触发时机、条件组、去向、剧情推进关系等事件深度编辑

也就是说，人物页中的“事件分栏”是关系组织入口，不是第二套事件编辑器。

## 6. 城市与建筑物需求

### 6.1 容器关系

- 城市是建筑物集合
- 建筑物是 NPC 集合

城市和建筑物功能相似，只是层级不同，因此在编辑器中应采用尽量一致的交互模式。

### 6.2 现有能力复用与非写死原则

城市与建筑物的功能设计必须遵循以下原则：

- 当前项目里已有的城市菜单、建筑交互、house module 功能族，可以作为默认能力来源
- 但剧本编辑器不应把当前项目中的具体建筑、具体名称、具体菜单项、具体交互写死为不可修改内容
- 创作者应能够在编辑器中：
  - 修改已有建筑名称
  - 修改已有建筑功能
  - 修改城市或建筑物的进入条件
  - 为城市或建筑物自由组合已有正式功能能力

也就是说，现有项目提供的是“可复用能力边界”和“默认模板来源”，而不是不可变的创作结果。

### 6.3 基础操作

城市和建筑物都应具备：

- 列表
- 新增
- 删除
- 点击进入详情页

### 6.4 菜单系统

城市与建筑物都需要有一个“菜单”能力。

菜单用于配置该对象对外暴露的基础功能入口，例如城市可包含：

- 风土人情
- 情报
- 地点
- 管理

同时：

- 菜单功能需要支持用户扩展
- 每个菜单功能都应可配置
- 菜单项按“入口绑定型”处理

### 6.5 城市菜单功能族

结合当前项目现状，城市应至少支持以下基础菜单功能族：

- 风土人情
- 情报
- 地点
- 管理

在特定剧情、身份或阶段下，城市还可以承载额外功能，例如：

- 化缘
- 特殊城市活动
- 阵营专属入口

这些功能族应被视为“城市默认能力模板”，后续仍允许创作者扩展新的城市菜单功能。

### 6.6 建筑物菜单功能族

结合当前项目现有建筑模块交互，建筑物应至少支持以下基础菜单功能族：

- 对话
- 交易
- 工作
- 休息
- 情报
- 小游戏
- 管理
- 离开

并允许根据建筑定位派生出更具体的可配置入口，例如：

- 买卖
- 疗伤
- 学习
- 赌博
- 舌战
- 配药
- 接活 / 提交
- 评定 / 议事

这些功能族应被视为“建筑物默认能力模板”，后续仍允许创作者扩展新的建筑物菜单功能。

### 6.7 建筑物自由搭配原则

建筑物不应被视为固定类型页面，而应被视为创作者可配置的功能容器。

这意味着：

- 当前项目中的药铺、茶馆、酒馆、住宅、寺庙、首领宅邸等，虽然可以作为默认参考模板，但不应在编辑器中被硬编码为唯一合法形态
- 创作者可以对已有建筑进行重命名
- 创作者可以调整已有建筑拥有哪些功能
- 创作者可以移除某些默认功能，也可以在正式能力边界内增加新的功能入口
- 不同建筑之间的功能组合应允许自由搭配，而不是被当前项目现状永久锁死

### 6.8 进入条件判断

城市与建筑物都应支持“是否允许进入”的条件判断能力。

该能力用于表达：

- 玩家在什么条件下可以进入某座城市
- 玩家在什么条件下可以进入某个建筑物
- 当前不满足条件时，应如何阻止进入或给出提示

进入条件判断应作为创作者可配置的正式能力，而不是只能通过代码写死。

### 6.9 进入态分层

结合当前项目现状，城市与建筑物的“进入”不应只区分为“能进 / 不能进”两种结果，而应支持更清晰的创作表达：

- 可见且可进入
- 可见但暂不可进入
- 当前阶段不显示

当对象“可见但暂不可进入”时，编辑器应允许创作者配置阻止进入后的反馈表现，例如：

- 拒绝提示
- 角色发言
- 引导性说明

这一能力用于承接当前项目中已经存在的“可见性”与“可进入性”分离思路，使创作者可以在不改代码的前提下配置“先看见、后解锁”或“被拦下并提示原因”的地点体验。

### 6.10 建筑入口挂接能力

结合当前项目现有建筑运行方式，建筑物除了“菜单功能”以外，还应支持若干基础入口挂接能力，用于描述玩家进入建筑后的默认行为。

建筑物应至少允许创作者配置以下类型的挂接关系：

- 进入建筑后默认落到哪个人物或入口
- 进入建筑时可触发什么内容
- 离开建筑时可触发什么内容
- 建筑返回上一级时回到哪个世界层级

这些挂接能力应被视为建筑编辑的一部分，用于复用当前项目已有的正式入口模型，而不是要求创作者通过额外代码接线。

### 6.11 菜单项绑定目标

菜单项可绑定到：

- 对话
- 事件
- 小游戏或交易入口
- 资料页或信息页

菜单项本身不承担完整业务逻辑，而是作为创作者可配置的入口。

### 6.12 菜单项最小交互约束

城市与建筑物菜单项虽然按“入口绑定型”处理，但编辑器仍需保证其具备最小可用交互能力。

每个菜单项至少应允许创作者配置：

- 中文名称
- 所属功能类别
- 绑定目标
- 是否显示
- 是否可用
- 不可用时的提示或说明

这样可以保证创作者不是只在编辑器里“挂一个空入口”，而是能完整表达该入口在当前阶段是否出现、是否能点、点不了时怎么反馈。

### 6.13 城市与建筑物菜单的扩展原则

城市和建筑物的菜单系统应遵循以下原则：

- 基础菜单功能族应可作为模板直接使用
- 创作者可以在基础功能族之外扩展新的菜单功能
- 新增菜单功能时，不要求修改运行时主壳层的固定分支
- 扩展功能仍应通过正式入口绑定方式接入，而不是临时硬编码

## 7. 剧情需求

### 7.1 剧情是正式核心对象

剧情不是事件或对话的附属字段，而是正式核心对象。

### 7.2 剧情定位

剧情按“剧情段落 / 章节容器”定义。

剧情负责：

- 组织人物、事件、对话的归属关系
- 表示内容属于哪一段剧情
- 承担创作组织视角下的内容容器职责

剧情不直接承担底层流程执行。

### 7.3 剧情与章节关系

当前采用较轻量的一期结构：

- 剧情对象直接携带章节字段
- 章节在当前阶段不是独立核心对象
- 章节主要作为剧情的正式归属维度存在

该方案用于降低当前阶段的信息架构复杂度，并优先保证剧情、事件、对话和预览链路可以闭环。

### 7.4 章节推进与玩家行为冲突规则

剧情与章节的冲突风险，不通过“把章节做成独立对象”自动解决，而是通过明确的推进规则解决。

应采用以下规则：

- 章节推进不能根据玩家当前位置或界面停留状态自动跳转
- 章节推进只能由明确的剧情完成、主线事件完成或等价的正式推进条件触发
- 玩家未满足某段剧情的前置条件时，后续剧情不能默认无条件发生

为避免出现“玩家一直没有离开寺庙，但后续主线却已经越章发生”这类冲突，剧情推进需要支持以下三类处理策略：

- 阻塞
  - 当前剧情未完成时，后续剧情与章节都不推进
- 等待
  - 当前章节保持不变，目标剧情处于待满足状态，直到玩家满足条件
- 强制收口
  - 当达到特定时间点、倒计时或主线收口条件时，触发替代事件、催促事件或强制回收剧情，使主线重新收束

至少应保证：

- 剧情对象能够声明其所属章节
- 剧情推进不会因为玩家未离开某地点、未触发某交互而让章节状态和已发生剧情互相矛盾
- 后续若要把章节升级为独立对象，不能推翻本规则中“章节推进由正式剧情条件驱动”的原则

## 8. 对话需求

### 8.1 对话职责

对话负责演出层内容，包括：

- 旁白
- 对白
- 选择
- 跳转

### 8.2 文本规范

- 所有文案都应走 `textId`
- 不允许在目标成品格式中内联文本
- 文案应可被策划独立编辑和维护

### 8.3 对话对象定位

“对话”应作为正式创作对象存在，但其职责应收口为“演出内容编辑”，不直接承担事件触发判断。

对话对象至少应负责：

- 编辑一段可演出的对白/旁白/选择支流程
- 承接事件进入后的内容呈现
- 为人物、剧情、事件提供可引用的演出内容单元

### 8.4 对话编辑器能力

对话编辑器至少应支持以下能力：

- 对话列表
- 新增对话
- 删除对话
- 编辑对话基础信息
- 编辑既有对话
- 编辑对话节点顺序
- 编辑节点类型与节点关系
- 编辑选择支去向

### 8.5 对话触发与后续动作能力

对话不仅是静态演出内容，还应支持创作者配置“对话结束后或对话过程中会触发什么”。

对话功能至少应支持把后续动作配置为：

- 触发小游戏
- 进入另一个对话
- 触发事件
- 切换到其他场景
- 切换到其他建筑
- 切换到其他城市

对话中的后续动作应被视为创作者可配置的正式能力，而不是只能通过代码硬接。

### 8.6 对话与人物、剧情、事件的关系

应采用以下关系约束：

- 对话不直接决定“何时触发”
- 事件负责决定何时进入某段对话
- 剧情负责决定该对话属于哪段内容组织
- 人物负责提供说话者、参与者和入口归属

### 8.7 对话预览要求

对话预览至少应支持：

- 单段对话播放预览
- 旁白、对白、选择支的顺序预览
- 选择支后的跳转预览
- `textId` 解析结果预览
- 对话后续动作去向预览

### 8.8 对话校验要求

对话相关校验至少包括：

- 节点引用完整
- 跳转目标存在
- 选择支目标存在
- 文本 `textId` 存在
- 说话人物引用存在
- 对话后续动作目标存在
- 不产生明显死链或空演出节点

## 9. 事件需求

### 9.1 事件职责

事件负责内容编排，即：

- 在什么时机触发
- 由什么条件控制
- 是否可重复
- 触发后进入哪段内容

### 9.2 事件编辑能力

事件编辑器至少要支持：

- 触发时机
- 条件配置
- 重复性配置
- 与人物、剧情、城市、建筑物的关联
- 与对话及小游戏绑定的衔接

### 9.3 事件对象定位

事件应是编排层核心对象，用于回答以下问题：

- 什么时候检查
- 是否满足触发条件
- 是否允许再次发生
- 触发后进入哪段内容

事件对象不承担长篇演出文本本体，也不直接承载完整小游戏机制。

### 9.4 事件基础配置能力

事件编辑器至少应支持：

- 事件列表
- 新增事件
- 删除事件
- 事件基础信息编辑
- 事件归属关系编辑
- 触发时机配置
- 重复性配置
- 进入目标配置

### 9.4.1 事件详情页结构

事件详情页不应做成松散堆叠的大表单，而应采用稳定的区块式结构，保证创作者按固定顺序完成配置。

事件详情页的主结构收口为以下五个区块：

- 基础信息
- 条件
- 去向
- 关联对象
- 预览与校验

各区块职责如下：

- 基础信息
  - 负责事件名称、触发时机、重复性、基础说明等总览信息
- 条件
  - 负责条件组与条件项编辑
- 去向
  - 负责事件触发后的目标去向配置
- 关联对象
  - 负责剧情、人物、城市、建筑物等归属与关联关系
- 预览与校验
  - 负责查看事件摘要、模拟进入结果和查看当前问题

该结构应采用单页分区编辑方式，而不是分步向导式流程。
原因是事件配置经常需要在条件、去向、关联对象之间反复来回调整，分步式更容易打断创作节奏。

### 9.5 事件触发结果能力

事件不仅要能决定“是否发生”，还要能决定“发生后进入什么”。

事件至少应支持将结果配置为：

- 进入某段对话
- 进入另一个事件
- 触发小游戏绑定
- 切换到其他场景
- 切换到其他建筑
- 切换到其他城市

事件触发结果应作为正式创作能力提供给创作者，而不是只能通过代码硬接。

### 9.6 事件与对话的关系

应明确：

- 事件负责决定何时进入对话
- 对话负责承载事件进入后的演出
- 事件可以进入对话，但不要求所有事件都必须先进入对话
- 对话中的后续动作也可以再回到事件或进入其他内容对象

事件与对话之间应形成可配置的编排关系，而不是单向死链。

### 9.7 条件编辑能力

条件编辑器至少应支持：

- 新增条件
- 删除条件
- 通过下拉框选择条件类型
- 通过下拉框选择比较运算符
- 通过分组方式表达：
  - 全部满足
  - 任一满足
  - 非
- 支持当前项目中正式允许的条件来源

### 9.7.1 条件编辑器交互形式

事件条件编辑器在交互上收口为“分组卡片式”表达，而不是树状流程图或步骤向导。

这意味着：

- 每个条件组以独立卡片或独立区块呈现
- 条件组内部可以新增多个条件项
- 条件组之间可以表达“全部满足 / 任一满足 / 非”这类组合关系
- 条件项通过下拉框选择条件类型与比较方式，再展示对应参数输入区

条件编辑器至少应支持以下操作：

- 新增条件组
- 删除条件组
- 条件组内新增条件
- 条件组内删除条件
- 条件组重排
- 条件项重排
- 复制已有条件组作为新条件组起点

条件编辑器不采用可视化连线或自由拖线式表达。

### 9.8 事件与剧情推进关系

事件不仅承担局部触发，也承担剧情推进承接。

应支持：

- 某事件属于哪段剧情
- 某事件是否是剧情推进节点
- 某事件完成后是否允许后续剧情进入“阻塞 / 等待 / 强制收口”中的某种状态

### 9.9 事件预览要求

事件预览至少应支持：

- 查看事件的触发条件摘要
- 查看事件将进入的目标内容
- 查看该事件与人物、剧情、地点、小游戏绑定的关联关系
- 在演出预览中模拟进入该事件后的内容流

### 9.9.1 事件去向、预览与校验联动

事件页中的“去向”“预览”“校验”不应彼此割裂，而应形成一个连续闭环。

至少应满足：

- 创作者在“去向”区块配置目标后，预览区能立即显示该目标摘要
- 若去向目标不存在、未完成或引用错误，校验区应立即给出问题提示
- 创作者可以从校验问题直接跳回对应去向配置位置
- 创作者可以从事件页直接预览“进入该事件后会去哪里、会触发什么”

对于不同去向类型，预览区至少应展示：

- 去向到对话：显示目标对话摘要并可进入演出预览
- 去向到事件：显示目标事件摘要并可继续查看链路
- 去向到小游戏绑定：显示绑定目标、前置条件、奖励与返回去向摘要
- 去向到地点切换：显示切换目标地点摘要

### 9.10 事件校验要求

事件相关校验至少包括：

- 触发目标存在
- 关联剧情存在
- 关联人物存在
- 关联城市 / 建筑物存在
- 条件表达式结构合法
- 事件去向明确
- 事件结果目标存在
- 不出现悬空事件入口

## 10. 小游戏绑定需求

### 10.1 小游戏绑定定位

- 小游戏绑定是核心对象之一
- 其职责是把现有预制玩法能力挂接到剧情、事件、人物、城市或建筑物入口中

### 10.2 边界

- 当前范围内不开发新的小游戏机制
- 当前范围内只处理绑定和调用关系
- 小游戏绑定应支持后续训练、交易、战斗等组合玩法场景

### 10.3 小游戏绑定对象定位

小游戏绑定不是玩法本体编辑器，而是一个正式的“调用配置对象”。

它至少应回答：

- 调用哪个预制玩法
- 从哪里调用
- 调用前需要满足什么条件
- 调用后回到哪里

### 10.4 小游戏绑定编辑能力

至少应支持：

- 小游戏绑定列表
- 新增绑定
- 删除绑定
- 选择绑定类型
- 选择调用目标
- 配置入口来源
- 配置基础说明文案
- 配置调用前条件
- 配置奖励
- 配置调用后返回去向

小游戏绑定在编辑器内部应以“统一绑定对象”进行管理，而不是分散写死在各对象页的私有结构中。

这意味着：

- 每个小游戏绑定都应是一个可独立查看、编辑、校验的正式对象
- 人物、对话、事件、城市菜单、建筑菜单等页面可以提供“就地创建绑定”的入口
- 但就地创建后，仍应落回统一的小游戏绑定对象进行管理与保存

### 10.5 小游戏触发条件与奖励

小游戏绑定除了声明“调用什么”，还应允许创作者配置：

- 在什么条件下允许触发
- 触发完成后可以获得什么奖励

这里的奖励配置应面向创作者表达为正式能力，而不是要求创作者通过代码手工补写结算逻辑。

### 10.6 小游戏绑定与其他对象关系

小游戏绑定应遵循以下约束：

- 小游戏绑定不应独立悬空存在
- 每个绑定都必须明确属于某个入口来源
- 人物、事件、对话、城市菜单、建筑物菜单都可以成为小游戏绑定入口
- 编辑器应明确展示“谁在调用这个小游戏绑定”

在入口模型上，应采用以下统一规则：

- 编辑器内部以“小游戏绑定对象”作为唯一正式承载对象
- 各入口对象只负责引用该绑定对象，而不是各自保存一套重复绑定内容
- 创作者可以从入口对象页反向创建绑定，但创建完成后应自动生成或指向统一绑定对象
- 同一个小游戏绑定若被多个入口复用，编辑器应明确显示其被哪些入口引用

### 10.7 小游戏绑定预览要求

小游戏绑定预览至少应支持：

- 查看入口来源
- 查看调用目标
- 查看调用前条件摘要
- 查看奖励摘要
- 查看调用后返回去向
- 在演出预览中看到“此处将进入某小游戏/交易/战斗入口”
- 对于项目当前已正式接入的小游戏，必须能够在预览中完整进入、完整游玩并返回

这一版中，小游戏不再满足于“入口级预览”或“仅占位提示”。
至少对于已纳入当前项目正式运行时的小游戏，编辑器预览必须做到：

- 可以从绑定入口实际进入小游戏
- 可以完成完整游玩流程
- 可以看到与正式运行时一致的结算与返回
- 可以验证奖励、后续去向和剧情衔接是否正常

### 10.8 小游戏绑定校验要求

小游戏绑定相关校验至少包括：

- 绑定目标存在
- 入口来源存在
- 返回去向明确
- 前置条件结构合法
- 奖励配置结构合法
- 不出现无人引用的孤立绑定

## 11. 预览需求

### 11.1 结构预览

结构预览用于帮助创作者检查：

- 当前对象之间的关联关系
- 引用是否完整
- 导出后会落到哪些内容结构

结合当前项目已有编辑器壳能力，结构预览应优先复用“对象树 + 检查摘要 + 导出状态”的工作台方式，而不是另起一套与编辑区脱节的预览页。

结构预览至少应能让创作者看到：

- 当前选中对象属于哪个对象族
- 它关联了哪些人物、城市、建筑物、对话、事件、剧情或小游戏绑定
- 它是否存在缺失引用、未完成配置或导出阻塞
- 它最终会映射到哪类正式产出

结构预览的目标不是替代最终运行时，而是让创作者在编辑阶段提前发现“对象关系不通”“目标缺失”“导出后无落点”这类问题。

### 11.2 演出预览

演出预览用于帮助创作者检查：

- 对话、旁白、选择支和跳转效果
- 事件触发后的演出流程
- 剧情、事件、对话在创作者视角下是否连贯

结合当前项目现状，演出预览应尽量复用正式运行时的场景展示路径，而不是在编辑器里另外维护一套只用于预览的演出渲染逻辑。

演出预览至少应支持：

- 从某个对话或事件入口开始预览
- 顺序播放旁白、对话、选择和跳转
- 展示 `textId` 实际解析后的文本结果
- 展示说话人归属与演出上下文
- 在到达小游戏、交易、战斗或地点切换入口时，明确提示即将进入什么目标

演出预览对不同入口的要求应区分处理：

- 小游戏：这一版必须支持完整可玩预览，而不只是入口提示
- 交易与战斗：这一版允许先提供入口级预览与去向确认，是否完整跑通留待后续版本收紧

因此，演出预览至少应做到：

- 能清楚展示“此处将进入什么玩法入口”
- 能展示进入前条件、完成后返回去向和奖励摘要
- 对小游戏入口，能够直接进入真实可玩的预览流程，而不是停留在占位提示
- 对交易与战斗入口，明确区分“当前为入口预览”还是“已经接入真实可运行预览”

### 11.3 预览与编辑联动

预览不应是脱离编辑流程的独立工具，而应成为创作者在编辑过程中的即时校对环节。

编辑器应支持以下联动原则：

- 在编辑对象时可以快速进入对应预览
- 在预览中能看到当前对象的来源与去向
- 预览发现问题后，创作者能快速返回对应编辑位置
- 结构预览与演出预览看到的问题，应能汇总到统一的校验或关注项区域
- 默认情况下，预览与校验按需打开，不要求与编辑区常驻同屏并列
- 对小游戏完整可玩预览，允许从当前工作台拉起扩展预览层，但仍属于当前工作台内部联动

### 11.4 预览文案与界面要求

预览区同样属于编辑器正式工作流的一部分，因此在被打开时必须遵循前文已经确认的编辑器原则：

- 使用中文标题与中文操作文案
- 不以英文标题、英文标签作为正式界面默认呈现
- 优先使用创作者易理解的说明，而不是底层技术术语直接外露

## 12. 导出目标

编辑器的产出仍然应落到项目当前可接受的合规 `scenario-pack`。

除了“可以导出”之外，还必须满足“导出的剧本可以正常运行”这一正式要求。

这意味着：

- 编辑器导出的剧本不能只是结构上可写出文件
- 导出结果必须能够被项目当前运行时正常加载
- 导出结果中的人物、城市、建筑物、对话、事件、剧情和小游戏绑定，必须能够按正式剧本流程被运行
- 导出结果若存在缺失引用、非法配置、无法进入的主流程或导出后无法运行的问题，应在导出前被校验阻止或明确提示

也就是说，导出能力的验收标准不是“成功生成文件”，而是“导出的剧本作为正式剧本产物可以正常进入项目并运行”。

该版本不引入新的运行时类型，也不引入与现有运行时平行的第二套执行机制。

### 12.1 导出映射原则

导出时，各创作对象不要求都对应一张全新的独立分表，但必须明确落入当前运行时已经接受的正式产物中。

导出映射应遵循以下原则：

- 项目级元信息导出到正式剧本包元信息文件
- 开局配置与场景包基础入口导出到正式场景包配置文件
- 人物导出到人物正式分表
- 城市导出到城市正式分表
- 建筑物导出到建筑正式分表
- 事件导出到事件正式分表
- 对话导出到场景正式分表，并把文案落到文本正式分表
- 剧情作为组织与推进对象，可以下沉到正式配置、事件和场景承载结构中，不强制要求独立导出分表
- 小游戏绑定作为调用配置对象，可以下沉到事件、对话、菜单入口或其他正式可调用结构中，不强制要求独立导出分表

### 12.2 导出映射落点

结合当前项目正式产物结构，导出落点至少应明确如下：

- 项目级信息导出到 `pack.json`
- 开局与场景包基础配置导出到 `scenario-profile.json`
- 人物导出到 `characters.json`
- 城市导出到 `cities.json`
- 建筑物导出到 `houses.json`
- 事件导出到 `events.json`
- 对话演出内容导出到 `scenes.json`
- 文案导出到 `text-entries.json`

对于“剧情”和“小游戏绑定”两类对象，应明确采用“下沉导出”原则：

- 剧情不强制生成独立文件，而是把归属关系、章节信息和推进关系下沉到正式可运行结构
- 小游戏绑定不强制生成独立文件，而是把调用目标、入口来源、返回去向和奖励关系下沉到正式可运行结构

### 12.3 导出覆盖原则

导出时应采用稳定、可预期的覆盖策略，避免创作者导出后出现“文件生成成功，但运行结果不确定”的情况。

至少应满足：

- 同一正式对象 ID 的导出结果应按正式覆盖策略生效
- 不允许因为导出顺序不同而得到不同运行结果
- 不允许生成缺失目标分表、悬空引用或无法解析的正式产物
- 不允许把仅用于编辑器组织的中间对象原样暴露为运行时无法识别的新格式

### 12.4 导出前校验原则

导出前必须经过正式校验，而不是在生成文件后再让创作者自行进游戏试错。

导出前校验应遵循以下原则：

- 会导致导出失败或运行时无法加载的问题，必须阻止导出
- 会导致内容不完整、链路中断或明显体验错误的问题，必须高亮提示并默认阻止导出
- 仅影响维护性或规范一致性的问题，可以作为警告提示，但不一定阻止导出

也就是说，校验结果至少应区分：

- 阻塞项
- 风险项
- 提示项

其中：

- 阻塞项：不修复就不能导出
- 风险项：可以继续编辑，但默认不应视为可交付状态
- 提示项：不影响当前运行闭环，但应提醒创作者补齐

### 12.5 当前项目兼容性确认

本 PRD 所定义的导出目标与当前项目运行时接受的正式产物方向一致，但不能被理解为“当前工程实现已经天然支持本 PRD 的全部导出内容”。

当前可以确认的是：

- PRD 中要求的正式产物落点与当前项目 `scenario-pack` 结构方向一致
- 人物、城市、建筑物、事件、项目级信息、场景包基础配置、文本条目等导出目标，与当前项目正式产物表面兼容
- “对话导出到 `scenes.json`、文案导出到 `text-entries.json`、小游戏绑定采用下沉导出”这一设计方向，与当前项目数据驱动运行时方向一致

当前不能直接视为已经完成闭环的是：

- 对话对象、剧情对象、小游戏绑定对象还没有全部补完到当前导出实现中
- 这些对象虽然已经在 PRD 中定义了正式职责，但仍需要通过正式 lowering 规则下沉到当前运行时可识别结构
- 在这些 lowering 实现完成之前，不能把“PRD 设计完成”直接等同于“当前项目已支持全量导出可运行”

因此，本 PRD 对兼容性的正式结论应表述为：

- 产物目标与当前项目兼容方向一致
- 当前工程还需要补完若干导出 lowering，才能让本 PRD 的全量对象闭环真正落到当前项目运行时中

### 12.6 当前实现缺口

结合当前项目现有导出实现，至少还存在以下三类导出缺口需要补完：

- 对话与故事流导出缺口
  - 需要把对话对象、故事流对象 lowering 到 `scenes.json` 与 `text-entries.json`
- 小游戏绑定导出缺口
  - 需要把小游戏绑定 lowering 到当前运行时可识别的调用结构，而不是停留在编辑器对象层
- 剧情下沉导出缺口
  - 需要把剧情对象的章节归属、推进关系 lowering 到 `scenario-profile.json`、`events.json`、`scenes.json` 或其他当前运行时正式结构

在这些缺口补完前，导出闭环只能被视为“部分兼容”，不能被视为“按本 PRD 全量对象已经完成可运行导出”。

## 13. 不做的内容

以下内容明确不纳入当前范围：

- 新的交易、战斗、小游戏底层玩法机制开发
- 全局字段 schema 可重定义
- 可视化连线式流程图编辑器
- 让创作者直接书写 TypeScript 或脚本
- 让菜单项本身演化为完整独立业务系统

### 14.1 剧情与章节的关系

### 14.2 工作台具体布局

当前已明确：

- 首页默认进入“项目总览”

  - 项目总览

  - 对话与事件

本项已收口，不再作为下一阶段的主要开放问题。

### 14.2.1 项目总览页内容深度

- 项目总览页是正式首页
- 项目总览页必须承载项目状态、创作进度、风险与阻塞、下一步操作入口

后续若要继续明细化，重点是：

- 创作进度区采用卡片摘要、统计块，还是按对象族清单展示
- 风险与阻塞区按严重级排序，还是按对象族归类展示
- “下一步操作入口”是推荐单一主行动，还是同时展示多个快捷入口

### 14.3 人物基础字段清单

后续若进入详细规格或数据契约设计，再单独明确：

### 14.4 城市与建筑物基础字段清单

- 进入条件判断与进入态分层的正式承载方式

### 14.5 对话编辑器边界

当前已进一步收口：

- 对话页的主职责是场景 / 演出编辑
- 人物对话入口组织可以在人物分栏中提供入口视图，但不应把对话页本体变成人物页的附庸
- 对话对象本身应支持配置后续动作去向，包括小游戏、其他对话、事件、场景和地点切换
- 人物页中的“对话分栏”只负责关系组织与入口跳转，不负责深度演出编辑
- 正式对话对象页是唯一的对话深度编辑位置
- 从人物页进入某段对话时，应跳转到该对话的正式对话页，而不是在人物页内展开一套完整编辑器
- 人物页中新建对话时，可以采用“创建后立即跳转到正式对话页”的方式进入深度编辑
- 正式对话页需要提供按人物筛选、按剧情筛选的视图，方便创作者按入口和内容归属查找对话

本项中的关系边界已收口如下：

- 人物页负责“这个人物有哪些对话入口”
- 对话页负责“这段对话具体怎么演出、怎么分支、怎么跳转”
- 两者之间通过跳转和关联同步，而不是各自维护一套独立内容

后续若要继续明细化，重点是：

- 人物页对话分栏中的列表粒度是只显示标题，还是同时显示归属剧情与状态摘要
- 正式对话页中的按人物筛选、按剧情筛选，是顶部筛选条还是侧边筛选区

### 14.6 事件编辑器交互细节

当前已进一步收口：

- 事件页必须支持条件组编辑
- 条件编辑优先采用下拉框和分组 UI
- 事件必须能明确关联剧情、人物、城市和建筑物
- 事件必须能配置触发结果去向，包括对话、事件、小游戏和地点切换
- 人物页中的“事件分栏”只负责关系组织与入口跳转，不负责事件深度编辑
- 正式事件页是唯一的事件深度编辑位置
- 从人物页进入某个事件时，应跳转到该事件的正式事件页，而不是在人物页内展开一套完整事件编辑器
- 事件详情页采用“基础信息 / 条件 / 去向 / 关联对象 / 预览与校验”五区块单页结构
- 条件编辑器采用分组卡片式表达，而不是树状流程图或步骤向导
- 事件页中的去向、预览、校验三者必须形成联动闭环

后续若要继续明细化，重点是：

- 各区块在事件详情页中是纵向展开、折叠面板，还是页内标签切换
- 条件组卡片中的摘要信息显示到什么粒度

### 14.7 小游戏绑定统一入口模型

当前已进一步收口：

- 小游戏绑定是独立配置对象
- 但其入口来源可以来自：
  - 事件
  - 对话
  - 人物分栏
  - 城市 / 建筑菜单项
- 编辑器内部采用“统一小游戏绑定对象”作为唯一正式承载模型
- 各对象页允许提供“就地创建小游戏绑定”的入口，但创建后应落回统一绑定对象
- 小游戏绑定主列表应放在“功能绑定”主区统一管理
- 各对象页中的小游戏入口配置应表现为“选择已有绑定”或“新建绑定并自动关联”，而不是各自维护一套私有绑定数据

本项中的入口模型已收口如下：

- 统一绑定对象负责承载调用目标、触发条件、奖励、返回去向等完整配置
- 入口对象负责声明“谁在调用这个绑定”
- 统一绑定对象与入口对象之间通过引用关系连接，而不是通过内容复制连接

后续若要继续明细化，重点是：

- 统一绑定对象的列表中如何展示“被哪些入口引用”
- 各对象页中的“选择已有绑定 / 新建绑定”入口是弹窗式还是侧栏式
- 小游戏触发条件和奖励配置在编辑器中如何表达与预览

当前已进一步收口：

- 开局与场景包基础配置导出到 `scenario-profile.json`
- 人物导出到 `characters.json`
- 城市导出到 `cities.json`
- 建筑物导出到 `houses.json`
- 事件导出到 `events.json`
- 对话演出内容导出到 `scenes.json`
- 文案导出到 `text-entries.json`
- 剧情与小游戏绑定采用“下沉导出”原则，不强制要求独立导出分表
- 导出必须遵循稳定覆盖策略，且不能产出运行时无法识别的新格式
- 当前项目兼容性应理解为“目标格式方向兼容”，而不是“当前工程已完成全量 lowering”

后续若要继续明细化，重点是：

- 小游戏绑定的入口来源、返回去向和奖励关系分别下沉到哪些正式结构
- 同 ID 覆盖、同名冲突和跨表引用时的最终优先级规则

### 14.10 校验清单

当前已进一步收口：

- 校验必须至少区分“阻塞项 / 风险项 / 提示项”三类结果
- 校验结果必须能回跳到对应对象或对应编辑位置
- 校验范围必须覆盖“能否导出”与“导出后能否正常运行”两层目标

校验清单至少应覆盖以下七类内容：

- 基础结构校验
- ID 与唯一性校验
- 引用完整性校验
- 触发与去向链路校验
- 文本与演出校验
- 导出映射校验
- 运行闭环校验

各类校验至少包括：

- 基础结构校验
  - 必填对象存在
  - 必填基础信息存在
  - 正式产物所需的最小结构完整
- ID 与唯一性校验
  - 对象 ID 唯一
  - 文本 ID 唯一
  - 不出现同层冲突或跨表非法冲突
- 引用完整性校验
  - 人物、城市、建筑、剧情、对话、事件、小游戏绑定之间的引用目标存在
  - `textId` 指向存在
  - 入口来源与返回去向存在
- 触发与去向链路校验
  - 事件触发目标存在
  - 对话跳转目标存在
  - 小游戏绑定入口与返回去向存在
  - 不出现明显死链、悬空入口或无目标去向
- 文本与演出校验
  - 不把正式文案内联到不允许内联的正式结构中
  - 对话与场景链路中的文案引用完整
  - 不出现空对白、空旁白、空选择支这类明显无效演出节点
- 导出映射校验
  - 各对象都能映射到当前运行时接受的正式产物
  - 不生成运行时无法识别的新结构
  - 下沉导出的剧情与小游戏绑定关系有合法落点
- 运行闭环校验
  - 至少一条正式主流程可以从开局进入
  - 主流程不会在关键节点无故中断
  - 导出后可形成“加载 -> 进入事件/对话/地点/小游戏 -> 返回后继续”的基本闭环

错误展示方式至少应满足：

- 在项目总览中显示汇总数量
- 在对象列表中显示对象级问题标记
- 在对象详情页中显示字段级或区块级问题提示
- 点击问题后可直接定位到对应对象或对应配置位置

后续若要继续明细化，重点是：

- 各类校验项分别归入阻塞项、风险项还是提示项
- 校验结果在项目总览、对象列表、详情页中的具体展示样式
- “运行闭环校验”是采用固定示例链路，还是允许创作者声明主流程链路作为校验基准
