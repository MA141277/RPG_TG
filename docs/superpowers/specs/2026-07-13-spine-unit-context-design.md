# Spine Unit Context Design

## 1. Goal

为 `tools/spine-node-timeline-editor.html` 增加“兵种上下文”能力，使制作者可以在工具顶部直接切换当前制作兵种，并让工具根据当前兵种：

- 自动加载该兵种对应的项目 JSON
- 只显示该兵种专属的编辑能力
- 保持通用编辑能力始终可用

本次设计的核心目标不是单纯减少按钮数量，而是把“兵种类型”和“兵种专属功能”收敛到统一配置层，避免继续把判断散落在各处的 `hidden`、`disabled` 和特殊分支里。

## 2. Scope

### In Scope

- 为 Spine 工具顶部新增兵种切换控件
- 在工具运行时增加显式的当前兵种上下文
- 为现有兵种建立统一配置表，至少覆盖：
  - `swordsman`
  - `archer`
- 切换兵种时自动加载该兵种对应的项目 JSON
- 将现有兵种专属功能分组到对应兵种名下显示
- 保留并复用现有的通用功能区，不对其做兵种隔离
- 增加针对兵种上下文和专属功能显隐的测试

### Out Of Scope

- 新增新的兵种资源或新的战斗逻辑
- 重写整个 Spine 工具布局
- 改动 JSON 文件格式
- 改动通用关键帧系统、播放系统和导入导出协议
- 为兵种切换增加本地持久化或用户偏好记忆

## 3. Current Repository State

当前 Spine 工具已经存在如下两类能力，但边界还不统一：

1. 顶部工具栏存在多个“快速加载/快速生成”按钮，例如 `newVersionSampleBtn`
2. 右侧属性区和绑定区混合承载了：
   - 通用功能，如记录关键帧、复制关键帧、节点编辑
   - 兵种专属功能，如刀光、箭矢、弓 rig

当前专属功能的显示规则主要依赖“当前是否选中了某个特殊部件”，而不是“当前正在制作哪个兵种”。结果是：

- 工具没有真正的兵种工作上下文
- 弓兵和剑士的专属能力混杂在同一套界面里
- 顶部加载入口和右侧功能显示没有统一关联
- 后续新增兵种时会继续增加散落的条件判断

## 4. Recommended Approach

采用“兵种配置表 + 当前兵种上下文”的方案。

### Why

- 这是最小改动下能长期扩展的方案
- 可以把“自动加载路径”“兵种专属功能组”“顶部文案”收敛到同一层配置
- 不需要重写整套 UI，只需要在现有结构上增加分组和统一显隐逻辑
- 以后如果新增枪兵、骑兵，可以继续往配置表中追加，而不是复制新的分支代码

### Rejected Alternatives

#### A. 只做按钮显隐，不建立兵种上下文

这种方案可以短期减少按钮冗余，但顶部加载、当前兵种、专属功能三者不会统一，后面仍然会回到 scattered condition 的状态。

#### B. 完全拆成独立的“剑士编辑器 / 弓兵编辑器”子面板

结构会更整齐，但改动过大，风险也高，容易破坏已有的通用工具和事件绑定，不适合作为本次最小落地方案。

## 5. Target Runtime Model

### 5.1 Current Unit Context

工具运行时新增显式状态：

```js
state.currentUnitType = "swordsman";
```

该状态用于统一驱动：

- 顶部兵种切换按钮的选中态
- 当前默认项目 JSON 路径
- 专属功能组的显示/隐藏
- 兵种相关快捷操作的可用性

### 5.2 Unit Config Registry

新增统一兵种配置表，例如：

```js
const SPINE_UNIT_CONFIGS = {
  swordsman: {
    label: "剑士",
    projectUrl: "/src/faxian/leg/swordsman/project.json",
    featureGroups: ["swordsman"],
  },
  archer: {
    label: "弓兵",
    projectUrl: "/src/faxian/leg/archer/project.json",
    featureGroups: ["archer"],
  },
};
```

这里的配置表是本次设计的唯一来源：

- 顶部按钮文案从这里取
- 自动加载路径从这里取
- 哪些专属功能组需要显示从这里取

实现时不允许再把项目路径和兵种显隐规则分散硬编码到多个函数里。

## 6. UI Structure

### 6.1 Top Toolbar

在 Spine 工具顶部新增“兵种选择”控件，位置在工具栏正上方或工具栏前部，以保证它是全局上下文而不是局部按钮。

最小形态建议为按钮组：

- `剑士`
- `弓兵`

要求：

- 始终可见
- 当前兵种按钮有明确激活态
- 切换时立即触发项目加载，不需要额外确认

### 6.2 Feature Grouping

现有功能分成两类：

#### Public Groups

这些功能保持原位，不参与兵种分类：

- 新建 / 导入 / 导出
- 播放 / 时间轴 / 帧切换
- 复制关键帧 / 粘贴关键帧
- 通用节点属性
- 通用贴图替换
- 通用绑定管理

#### Unit-Specific Groups

这些功能仅在对应兵种上下文出现：

`swordsman`:

- 刀光出现 / 消失
- 本动作隐藏刀光
- 重置本动作刀光状态
- 刀光父节点绑定相关控件
- 剑士武器相关快捷能力

`archer`:

- 弓 rig 创建或安装相关控件
- 箭矢创建或安装相关控件
- 箭矢出现 / 消失
- 重置本动作箭矢状态
- 箭矢父节点绑定相关控件

## 7. Behavior Rules

### 7.1 Switching Units

切换兵种时，工具必须按以下顺序执行：

1. 读取目标兵种配置
2. 请求并加载对应 `projectUrl`
3. 成功后更新 `state.currentUnitType`
4. 刷新专属功能组显隐
5. 重新渲染全部界面
6. 提示当前已切换到哪个兵种

### 7.2 Load Failure Rule

若目标兵种 JSON 加载失败：

- 当前项目数据保持不变
- 当前兵种上下文保持不变
- 不允许出现“按钮已经切走但工程没有切走”的半成功状态
- 向用户提示加载失败和目标兵种

### 7.3 Group Visibility Rule

兵种专属功能显示采用两层判断：

1. 第一层：当前兵种上下文决定该分组是否渲染
2. 第二层：当前选择对象决定分组内按钮是否可用

这意味着：

- 切到剑士时，弓兵专属分组整体不出现
- 切到弓兵时，剑士专属分组整体不出现
- 即使当前没有选中刀光或箭矢，对应兵种专属分组也可以保留结构，但按钮应按现有规则禁用或局部隐藏

该规则的目标是“先按兵种裁剪界面，再按对象裁剪交互”。

## 8. Implementation Boundaries

### 8.1 Allowed Changes

- 修改 `tools/spine-node-timeline-editor.html`
- 为兵种上下文增加必要的状态和渲染函数
- 为测试增加新的 HTML 结构与逻辑断言

### 8.2 Disallowed Changes

- 不得重构与本功能无关的时间轴、拖拽或渲染主流程
- 不得改动 JSON schema
- 不得把兵种判断散落回单个按钮监听器内部
- 不得通过删除通用功能来“减少按钮冗余”

## 9. Testing Strategy

至少补齐以下验证：

- 存在统一兵种配置表，且包含 `swordsman`、`archer`
- 切到 `swordsman` 时会尝试加载 `swordsman/project.json`
- 切到 `archer` 时会尝试加载 `archer/project.json`
- 加载成功前不更新当前兵种上下文
- 剑士上下文不显示弓兵专属功能组
- 弓兵上下文不显示剑士专属功能组
- 公共功能区在两种兵种上下文下都保持可用

## 10. Acceptance Criteria

当以下条件全部成立时，本次设计视为完成：

- Spine 工具顶部存在清晰可切换的兵种选择控件
- 当前兵种切换会自动加载对应兵种 JSON
- 切换失败不会污染当前工程和当前上下文
- 剑士只看到剑士专属功能和通用功能
- 弓兵只看到弓兵专属功能和通用功能
- 复制关键帧、播放、导入导出等公共功能不受兵种切换影响
- 兵种路径、标签和专属功能显隐规则统一收敛在配置表中
